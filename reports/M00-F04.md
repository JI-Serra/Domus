# M00-F04 (+ M00-F03 context wiring): authentication and real active context

Implemented Supabase Auth (email + password, magic link, password recovery, logout) with cookie sessions via `@supabase/ssr`, default-deny route protection in the Next proxy, and the real active context (validated server-side on every request) replacing the mock provider. Covered by unit tests, a Playwright suite (Chromium, 1440 px and 360 px projects) and a new CI `e2e` job. No migration or DB contract change; no `service_role` anywhere in the web app.

## How the requirements are met

- **Cookie sessions, es-AR routes.** `/ingresar` (password or magic link), `/recuperar`, `/restablecer`, `/auth/callback`. Logout is a server action (`signOut({ scope: 'local' })`, forgets the context cookie).
- **Error mapping.** `mapAuthError` turns Supabase `code`/`status`/`name` into `auth.errors.*` keys (invalid credentials, unconfirmed email, rate limit, expired link, network, weak/same password, expired session, unknown). The raw English message is never shown; a test enforces that every key has an es-AR message. Validation errors (empty/invalid email, short password, mismatch) are es-AR too and attached to their field.
- **No user enumeration.** Recovery and magic-link requests answer "sent" for any email; errors that depend on the account existing (`user_not_found`, `otp_disabled`, `signup_disabled`, …) are swallowed. Magic links use `shouldCreateUser: false`. Only rate-limit/network errors are surfaced. Covered by e2e (unknown email shows the same confirmation).
- **Route protection.** Default deny in the proxy (public: `/ingresar`, `/recuperar`, `/restablecer`, `/auth/*`, `/design*`, `/api/debug/error`). Unauthenticated → `/ingresar?next=<path>`; `next` is only honored when it is a same-origin relative path (`safeNextPath`, tested against `//`, backslashes, absolute URLs, control chars). A signed-in user opening `/ingresar` is sent home. The `(app)` layout re-checks the session, and Server Actions verify it themselves, so the proxy is not the only gate. Session refresh follows `@supabase/ssr` guidance: `getClaims()` in the proxy, refreshed cookies and the library's no-cache headers copied to the response.
- **Real active context.** `loadMemberships` selects `membership` joined with `tenant`, pinned to `person.user_id = <verified user id>`. The pin matters: registry and admin-management admins can read _other people's_ memberships in their tenant (verified: `admin.ceibos` sees 6 rows unfiltered), so an unpinned query would offer someone else's context. Status/window are filtered in SQL and checked again by the resolver. Default = first option by tenant name (es-AR collation), then role, then id. The cookie (`domus-context`, httpOnly, SameSite=Lax, secure on https) is only a _request_, re-validated on every request in the proxy, the layout and the switch action. Switching = `switchContextAction`, which accepts only ids in the freshly computed options. Unit is `null` (slot kept). Query errors throw instead of rendering the empty state.
- **Platform context.** `Plataforma` is offered last and only when the session is `aal2` and an active `platform_admin` row is visible (RLS already requires `aal2`). The forged `platform` cookie is ignored otherwise (e2e). TODO for M01-F05 (MFA enrollment) is that nothing enrolls MFA yet, so the option cannot appear for the seeded `platform@domus.local`.
- **No memberships.** Empty state "Todavía no tenés un barrio asignado" with logout (e2e uses a throwaway account).
- **Observability headers.** The proxy deletes any client-sent `x-domus-tenant-id` / `x-domus-membership-role` and sets them from the validated context (tenant id omitted for the platform context). `instrumentation.ts` now imports the header names from `lib/context/headers.ts`. Covered by `proxy.test.ts` (spoofed values overwritten or removed).
- **Isolation demo (e2e).** As `admin.ceibos`, supabase-js reads its own tenant, and `tenant`, `person`, `membership`, `membership_permission` filtered by Las Tipas' id all return `[]`; an update against a Tipas person affects nothing; a barrio user sees no `platform_admin` rows.

## Decisions and things to know

1. **`supabase/config.toml` changed** (not a migration): `auth.additional_redirect_urls` now also allows `http://127.0.0.1:3000/**` and `http://localhost:3000/**`. Without it, magic-link and recovery emails can redirect only to the bare `site_url`, so developers on `localhost` would land without the PKCE verifier cookie. Restart the stack after pulling (`pnpm supabase stop && pnpm supabase start`; data is kept). The e2e tests use `127.0.0.1`, which is `site_url`.
2. **Redirects use the request host headers, not `request.nextUrl`.** In route handlers `nextUrl` reported `localhost` under `next dev -H 127.0.0.1`, which dropped the session cookies on the redirect. `siteUrlFromHeaders` (x-forwarded-* aware) is used for redirects and for the email link origin. Confirmed by a failing then passing magic-link e2e.
3. **Magic links are PKCE**, so a link only works in the browser that requested it; a link opened elsewhere (or reused) shows the "El enlace venció o ya se usó…" message with advice to open it in the same browser. An OTP-hash flow (`?token_hash=&type=`) is also handled by the callback for later cross-device templates.
4. **Mock provider removed.** `MockActiveContextProvider` is gone; its four fixtures live on as `src/test/fixtures.ts` for component tests. `ActiveContext` moved to `@domus/domain/context` (`tenant_id`/`tenant_name` are nullable for the platform context) and `active-context.tsx` re-exports it. `ActiveContextProvider` now follows a changed `initialMembershipId`, and `ServerActiveContextProvider` persists switches through the server action then refreshes.
5. **Switch is optimistic.** The UI changes immediately and the cookie is written when the server action returns; a reload in that short window would keep the old context (the e2e waits for the cookie).
6. **Password policy** in the UI is ≥ 8 characters (the local Supabase minimum is 6); the auth server still enforces its own rules (`weak_password` is mapped).
7. **Rate limits.** Local `config.toml` rate limits were not touched and the suite ran 3 times in a row without hitting them (the local mail catcher does not enforce `email_sent`).
8. **E2E layout.** Specs run serially (one worker): they share one Supabase stack and one mailbox, and `clearMailbox()` empties Mailpit. Throwaway accounts come from public sign-up (local confirmations are off), so no admin key is needed. `@supabase/supabase-js` is a dev dependency of `apps/web` for the isolation demo only.
9. **CI `e2e` job** (not run here; it needs GitHub runners): starts Postgres, Auth, the gateway, PostgREST and Mailpit only, exports `NEXT_PUBLIC_SUPABASE_*` from `supabase status -o env`, builds, runs Playwright against `next start`, and uploads `apps/web/playwright-report` and `test-results` as the `playwright-report` artifact on failure. The excluded-services list should be checked on the first real run.
10. **Tooling.** `pnpm exec prettier --write` reformats `tokens.generated.css` when pointed at `apps/web/src`; I restored it (the sync test guards it). Local `apps/web/.env.local` (git-ignored) holds the local anon key.
