# M02 registry database contract (T14 + T18 / H2)

Implemented M02-F01–F08 and the M01-F03 billable-unit count in nine new migrations (`20261011000000`–`20261011000008`). H0/H1 migration files and application UI files are unchanged. This report is the contract for the subsequent registry UI tasks. T18 extends the resident contract in migrations `20261011000009` through `20261011000011`; see `reports/T18-contract-additions.md` for current acceptance evidence.

## Decisions and security

- D17: optional `membership.unit_id` and `invitation.unit_id` have composite tenant FKs. Only `unit_holder`/`household_member` memberships carry a unit; promotion to another role clears the unit. People remain tenant scoped; one Auth identity can consent to several unit memberships without rebinding its person identity.
- D20: `billable_unit_count` includes nonarchived units whose status is in `tenant_billable_unit_statuses`; nullable `unit_is_billable` overrides that criterion. The existing H1 default includes all three statuses. Platform administrators need the existing MFA identity validation; tenant administrators can count their tenant without registry permission.
- D22: a unit join code requests review and never grants access. The coordinator approved the join/pairing design before implementation. Codes contain twelve unambiguous base32 characters, are displayed in groups of four, accept case/space/hyphen normalization, and only SHA-256 hashes persist. Rotation invalidates the old secret. A verified, nonsupport authenticated user has five attempts per fifteen-minute window; failed tenant attempts have a separate 100/window counter that never blocks a valid code. Invalid, rotated, throttled, archived, foreign, malformed and unavailable submissions return the same `{ "status": "unavailable" }` shape. Counters persist across failed HTTP requests.
- D23: permissions are `view_unit_finance`, `book_amenities`, `manage_access_authorizations`. New household membership defaults to only `manage_access_authorizations`. An eligible holder or registry administrator replaces a member's permission set through the RPC; self-grants are forbidden. Minor residents cannot receive accounts or permissions. Birth-date corrections synchronize minor flags, remove holder flags, revoke memberships and pending invitations, and still must preserve the occupied-unit holder invariant.
- D24: guards lose the broad `person` SELECT policy. Their ordinary person query returns only their own profile. `guard_registry` provides operational names/unit/holder/minor fields, with no document, birth date, email or phone fields. Backup phone lookup requires explicit `approval_phone_fallback` operation intent and records an audit event without the phone value.
- Every new tenant table has RLS, composite tenant relationships and isolation coverage. Policies use set-returning central identity helpers. `registry_writer` is an isolated NOLOGIN/NOINHERIT role without BYPASSRLS, client membership or schema CREATE privileges; authorized SECURITY DEFINER entry points check identity and scope before looking up targets. Permission/role writes remain RPC-only. Integrity triggers also run under replica mode.
- Audit records retain structural changes but redact names, email, document data, phone numbers, birth dates, plate codes, photo paths, staged row JSON and all secret hashes. Audit remains append-only. Support sessions are bound to their tenant and target scope; onboarding secrets/decisions and device identities exclude impersonation. Suspended tenants remain readable and reject these mutations; cancelled tenants disappear from tenant reads. M05 can later add its narrowly authorized suspended-gate operation.
- An occupied, nonarchived unit must have continuous adult-holder coverage from now onward, not merely a currently active holder whose sole relationship later expires. Deferred constraints permit atomic holder replacement; RPC creation/import flushes the invariant before returning. Unit deletion is unavailable; archival preserves history and revokes unit account invitations/memberships.

## Public RPCs

All new public RPCs allow authenticated callers only; anon and service-role invocation are revoked. UUID arguments below are UUIDs; `client_event_id` is a required UUID where shown. Mutations with receipts bind actor, tenant, operation and payload to the event; reuse with different input is denied. Secrets are never stored in receipts. Join requests instead deduplicate by event and by pending actor/unit; a retry returns the existing request rather than modifying its submitted data.

`registry` means an active tenant administrator with that administrative permission, `guards` means the corresponding guards permission, and `holder` means an active adult unit-holder membership with an eligible residence. Read operations honor subscription and support identity rules. Unauthorized/missing scoped targets consistently use SQLSTATE `42501`; input errors use `22023` or native constraint errors, and occupied-holder violations use `23514`.

## Payloads and client flow

Use `@domus/domain/registry` Zod schemas and `@domus/supabase/registry` typed wrappers. Generated Supabase types remain the source of row and RPC argument types. Save payloads are full replacements for editable fields: omitted optional fields clear/default them, rather than acting as JSON patches.

- Unit: optional `unit_id`, required `unit_code`, optional `unit_block_code`, `unit_lot_number`, `unit_contact_phone`, `unit_backup_phone`; `unit_status` defaults `vacant`; positive `unit_coefficient` defaults 1; nullable `unit_is_billable` inherits criteria. `save_unit.residents` entries are `{person: person_data, resident: resident_data}`.
- Person: optional `person_id`, required `person_first_name`, `person_last_name`; optional document type/number pair, normalized email, phone and ISO birth date. Natural lookup uses tenant document/email; Auth `user_id` cannot be supplied or changed through these RPCs.
- Resident: `unit_resident_relationship` (`owner`, `tenant`, `family`, `other`), `unit_resident_is_holder`, `unit_resident_is_minor`, optional `unit_resident_valid_from_at`/`unit_resident_valid_to_at` ISO timestamps. End residence through the latter; no deletion operation. Recorded birthdays can establish minority regardless of caller's flag.
- Vehicle: optional `vehicle_id`, required `vehicle_plate_code` (uppercase alphanumeric normalization, 3–12 characters), optional make/model/color and `vehicle_archived_at`.
- Pet: optional `pet_id`, required `pet_name`/`pet_species_name`, optional breed/photo path/archived timestamp. Upload to private `pet-photo` bucket using `tenant_id/unit_id/filename`; 2 MiB PNG/JPEG/WebP. Storage policies bind the complete tenant/unit path; members read their household, unit managers write. Persist the object path, not a public URL.
- Gate: optional `gate_id`, required `gate_name`, `gate_kind` (`vehicular`, `pedestrian`), `gate_is_active` defaults true.
- Join submission derives the tenant from the globally unique code hash when `target_tenant_id` is omitted or null. Named HTTP arguments remain compatible; SQL positional callers must use `(join_code, person_data, client_event_id, target_tenant_id)` or named notation. No legacy overload remains. Join submission accepts first/last name, optional document pair/birth date; email comes from the verified Auth identity. Minor declarations/dates are rejected. Approval returns `{status:'approved', invitation_id, invitation_client_event_id, person_id}`; rejection returns `{status:'rejected'}`. Approval creates an unbound resident plus pending invitation, without an account membership.

Deliver resident invitations through `sendResidentInvitation` / `send-invitation`, passing `target_unit_id` and `target_person_id`. For an approved join request, pass the returned invitation event/person, submitted email and chosen role so Edge retries that invitation and emails its newly issued secret. The ordinary H1 email-link proof and `accept_invitation(token)` remain mandatory. A delivered retry returns a null secret and avoids duplicate delivery; undelivered retries rotate it. Invitations expire after seven days, are one-time and store only hashes. Consent cannot bind a person already linked to another Auth user, and the legacy H1 anti-rebinding cases continue to pass.

Pairing returns a separate random 256-bit device credential only on redemption; only its hash persists. The device has its own identity, gate and paired-by operator record. Sync requires both an authorized operator identity and device credential; pairing is groundwork for M13, not a general guard authentication bypass. Expired, reused and revoked credentials return uniform unavailable status.

The unit sheet contains `member_permissions`, `unit`, `residents`, active `vehicles`/`pets`, `memberships`, `pending_invitations`, `pending_join_requests`, `permissions`, and `movements: []`. The `member_permissions` object maps household membership UUIDs to their explicit `household_permission[]` grants (empty arrays for members without grants). Only active eligible holders of that unit or tenant registry administrators receive this map; other callers receive `{}`. Support follows the target's rights inside the bound tenant. Registry/holders see resident personal details; members see other residents' display names and their own profile. `user_id` and invitation hashes are omitted. Membership and pending arrays are empty for members; support identities never receive pending onboarding arrays. `balance: null` appears only with finance permission, and `authorizations: []` only with access permission. Booking capability is expressed in `permissions`; corresponding modules populate their own data later.

## Import row schema and idempotency

CSV/XLSX parsing belongs to the UI. Send a strict flat JSON array; numbers and booleans must already have those JSON types. Empty optional cells should become null/omitted, not empty strings. The fixture is `supabase/fixtures/registry-demo-150.csv`; regenerate with `node supabase/fixtures/generate-registry-demo.mjs`, optionally `--units 2000` for a larger fictional sample.

| Columns                                                   | Rule                                                                           |
| --------------------------------------------------------- | ------------------------------------------------------------------------------ |
| `unit_code`                                               | required trimmed string, 1–100 characters; tenant/case-insensitive natural key |
| `unit_block_code`, `unit_lot_number`                      | optional strings up to 100 characters                                          |
| `unit_status`                                             | occupied / under_construction / vacant; default vacant                         |
| `unit_coefficient`                                        | positive number below 100,000,000; default 1                                   |
| `unit_is_billable`                                        | optional boolean/null                                                          |
| `unit_contact_phone`, `unit_backup_phone`, `person_phone` | optional nonempty strings up to 32 characters                                  |
| `person_first_name`, `person_last_name`                   | both required if person data is supplied; trimmed 1–100 characters             |
| `person_document_type`, `person_document_number`          | optional pair; dni/passport/other and trimmed 1–32 characters                  |
| `person_email`                                            | optional normalized email; document or email required for any resident         |
| `person_birth_date`                                       | optional ISO date, cannot be future                                            |
| `unit_resident_relationship`                              | owner / tenant / family / other; default other                                 |
| `unit_resident_is_holder`, `unit_resident_is_minor`       | booleans; default false; holder must be adult                                  |

No UUIDs, Auth bindings, role grants, valid-time overrides or unknown fields are accepted in import rows. Several rows can describe one unit and several units can reference one person, but repeated unit attributes/person data/relationship flags must agree. Preview reports errors such as `unit_rows_conflict`, `person_rows_conflict`, `person_identity_conflict`, `resident_rows_conflict`, `unit_archived`, `self_role_change`, `occupied_unit_requires_holder` and field-specific invalid/required codes. Local validation returns `{row_number,data,errors:[{field,code}]}`; authoritative DB preview returns persisted rows with `registry_import_row_number`, `registry_import_row_data`, and `registry_import_row_errors: string[]`. Translate codes through the UI's es-AR messages; do not display raw SQL error text.

Confirmation revalidates against current data and applies units, people and residents in one transaction. Natural keys are case-insensitive unit code; document type/number or normalized email; then tenant/unit/person residence. Conflicting identities do not silently merge. Reimport of identical data leaves live rows, timestamps and their audit history unchanged, while the new staging batch retains its own audit trail. Import never creates accounts or invitations. Only the two bulk RPCs have a 120-second SQL timeout; other operations keep the existing role timeout. PostgREST hoists the per-function timeout into the HTTP transaction ([PostgREST documentation](https://docs.postgrest.org/en/stable/references/transactions.html#hoisted-function-settings)); full-scale HTTP acceptance verifies this behavior locally.

## Seed and performance evidence

Both tenants have forty units (28 occupied, seven under construction, five vacant), holder coverage, linked existing seeded resident accounts, 28 vehicles, fourteen pets, one gate and one device. Seed device tokens are random and discarded: pair a fresh test device to exercise credential flow. The 150-unit HR-02 CSV contains 450 residents including minors and a holder for each occupied unit.

`supabase/probes/registry-performance.sql` builds 2,000 units/6,000 residents inside a rolled-back transaction and captures EXPLAIN ANALYZE for admin search, the 360 sheet and their indexed underlying predicates. Recorded output is `reports/M02-performance.txt`: staging 43,405 ms; confirmation including occupied-holder constraints 50,897 ms; narrow search 10.703 ms; broad search 19.760 ms; unit sheet 6.697 ms. The resident/person join uses tenant-leading composite indexes and completes in 3.546 ms. PostgreSQL chooses a sequential unit scan for the small 2,080-unit fixture; trigram indexes exist for growing unit code, person display name/email and vehicle plate data. These are local warm-database measurements, not a production latency guarantee.

Real HTTP acceptance (`node supabase/probes/registry-scale.mjs`) passed with 6,000 staged rows in 38,190.1 ms, atomic confirmation of 2,000 units/6,000 residents in 50,663.2 ms, search in 30.8 ms and unit sheet in 13.2 ms. This exercised actual Auth/PostgREST requests and the bulk RPC timeout, not an owner connection. A subsequent clean reset removed the scale dataset before the final security probes.

## Integration boundaries

No UI changes were made. Adapt future guard consumers to `guard_registry` and explicit backup contact access. Inspection found no existing e2e assertion requiring the former broad guard person list; existing browser suites were not run for this DB-only task. E2E fixture utilities that create household roles without a unit should be updated when those tests exercise the new registry flows. M05 supplies actual approval-request context for backup contact lookup; this groundwork currently validates operation intent and audit attribution. M04/M07/M08 populate financial, amenity and access placeholders, and M13 adds device offline/operator workflows.

The cloud project is unchanged; integration and staging migrations belong to the orchestrator.
