## What was built

- **Onboarding**: `/invitations/accept` already worked for unit roles; the accept action now lands residents in `/home` (others still in `/`). Residents see a one-line privacy notice with the full text (Ley 25.326) behind an info button, before creating their account, also on `/join` (`components/privacy`).
- **Active context carries the unit** (`membership.unit_id` / `unit.unit_code`): top bar shows "Titular · Mz 1 Lote 1".
- **`/join`** (`app/(account)/join`, works with or without memberships): code field formats pastes to `XXXX-XXXX-XXXX` (case, spaces, hyphens), name + optional document, privacy notice; "Solicitud enviada / Pendiente de aprobación"; own requests with status and cancel (confirmation). A malformed code, an unknown one, a rotated one or a throttled attempt all produce the same message; the e2e asserts the two paths render the same error text. The tenant is derived from the code by the server (T18). Entry points: "Tengo un código de unidad" on the no-barrio page and a link on Inicio.
- **Mi hogar `/home`**: holder: members (add by email, minors without account, invite existing resident, resend/revoke invitation), per-member delegations (3 toggles, complete set sent each time, rollback on refusal; minors and non-accounts get none), vehicles (plate hints behind an info button, normalized, add/edit/remove), pets (name, species, breed, optional photo), pending join requests (approve → invitation email through `send-invitation`, reject), unit code (generate/rotate with confirmation, shown once with copy). Member: household read-only, own data, "Habilitado para vos" with only the delegated cards. Tab bar: Inicio · Mi hogar · Accesos · Barrio · Cuenta.
- Everything the UI shows comes from `unit_sheet`; writes go through the registry RPCs from Server Actions that take tenant/unit from the server-validated context, never from the form. Idempotency keys per form (`client_event_id`; separate key for the invitation step so retries after a failed delivery don't duplicate).
- Shared primitives (additive, `components/ui`): **`Sheet`** (bottom sheet on mobile, modal ≥ sm; Escape closes an open info popover first) and **`FilePicker`** (localized file button). The admin worker had created no file picker, so this one is new — **orchestrator: the admin UI can reuse it**.
- Domain (`@domus/domain/household`): permission toggling, resident standing, plate classification/format, join-code input formatting, form schemas, pet photo path rules.

## Decisions and things to know

1. **Contract gaps answered by the coordinator (A)**, implemented by T18: tenant-less `submit_unit_join_request`, `my_unit_join_requests`, `cancel_unit_join_request`, `unit_sheet().member_permissions`.
2. **T19 consequence — holders cannot edit an account member (removal came with T20, see T16b below).** After T19, `save_resident` lets a holder change only residents they registered who are unbound and never invited. So "edit relationship / end membership" is offered only for people **without account and minors**; invited people can be re-sent/revoked (after revoking they are editable again); account members only get the delegation toggles (e2e proves the database refuses ending one). To let holders end an account member the DB needs a holder-authorized RPC (e.g. `end_household_membership`); not built here (no DB changes per the brief). Reported to the coordinator.
3. **T19 integration bug found and fixed by T19** (reported as a blocker during the run): a bound person with `person_claimed_*` could not read their own `person` row, so the H1 context loader returned no membership for holder-registered members; migration 021 fixed it, the e2e covers it.
4. **Unit code "show"**: the DB stores only a hash, so an existing code can't be shown. The holder generates a code (the old one stops) and sees it once.
5. **Pet photos** are uploaded by the browser straight to the private `pet-photo` bucket (avoids the 1 MB Server Action body limit) and only the path is sent; the server checks it belongs to this unit's folder. Choosing a photo and then cancelling leaves an orphan object in the private bucket (holders can delete in the Storage API; no cleanup job exists).
6. **Shared e2e stack**: the Edge Function and Auth allow-list build email links for `http://127.0.0.1:3000`, so runs on another port landed on the wrong server. `e2e/support/auth-links.ts#openAuthLink` reads the Auth redirect and replays its path/query/fragment on the page's own origin; it replaced `page.goto(link)` in `auth.spec`, `backoffice.spec` and `screenshots-backoffice.spec` (behaviour on port 3000 is identical). The admin worker's specs may need the same.
7. **E2E cleanup helper** `cleanUpResidents` archives the units, removes registry rows and, in a separate transaction, disables the `protect_registry_relationships` trigger on `public.unit` only long enough to delete the units of the test barrio (units can't be deleted through the product), then re-enables it (`enable always`). Local test database only.
8. `lib/platform/form-state.ts`: success state gained an optional `value` (the freshly generated code). `lib/context/load.ts` + `@domus/domain/context`: optional `unit_id`/`unit_code` (backwards compatible).
9. Not done / follow-ups: resident delegated modules (finance, amenities, access passes) are placeholders until M04/M07/M08; no holder-side "end account member" (see 2); `Inicio` for residents is still the shell placeholder besides the new join link.

## T16b — remove account members (T20 `end_household_membership`)

Merged `main` (T20, migrations 22-23). In `/home` a holder now sees **Quitar** on a household member **with an account** (never a holder, never themself): a confirmation states the effect ("Pierde el acceso a la unidad. Sus datos no se borran."), then `removeAccountMemberAction(membershipId)` calls `endHouseholdMembership` with a fresh `client_event_id` and the page refreshes. The action re-checks on a fresh unit sheet that the membership belongs to a non-holder, non-self household member with an account; the database decides again. Identity editing stays as T19 requires: account members still get no Edit.

- New resident standing `former` ("Sin acceso"): after removal the person stays in the unit sheet (data kept) but is bound to an Auth identity, so the UI offers no Edit/Quitar/Invitar for them (the database would refuse). Covered by domain tests.
- Tests: component (confirm text, membership id sent not person id, refusal, nothing offered for holders/former), server action (event key per call, never sent for holders/unknown/no-account, refusal, read-only barrio), domain (`former`). E2E (360 + 1440): holder removes an account member and the member loses the unit context on the next load (and on `/`), the person stays listed as "Sin acceso"; a co-holder is shown without actions, and direct `end_household_membership` on the co-holder and on the holder's own membership both fail with `42501`.
- E2E helper `addCoHolder` inserts the second holder straight into the local test database (the product creates holders only through registry administrators and invitations). Screenshots in `docs/screenshots/h2` were refreshed.
