## Schema inventory

All six tables have UUID primary keys defaulting to `gen_random_uuid()` and RLS enabled. All five mutable tables have database-maintained `<table>_created_at` and `<table>_updated_at` timestamptz columns. Audit events use immutable `audit_event_occurred_at` instead. Timestamps represent UTC instants; the default display zone is `America/Argentina/Tucuman`.

| Table                   | Columns                                                                                                                                                                                                                                                                                               |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `tenant`                | `tenant_id`, `tenant_name`, `tenant_slug` (unique), `tenant_address`, `tenant_time_zone`, `tenant_subscription_status` (default `pilot`), `tenant_settings` (JSON object), `tenant_logo_path`, `tenant_created_at`, `tenant_updated_at`                                                               |
| `platform_admin`        | `platform_admin_id`, `user_id` (unique, FK to Auth), `platform_admin_is_active`, `platform_admin_created_at`, `platform_admin_updated_at`                                                                                                                                                             |
| `person`                | `person_id`, `tenant_id` (required FK), `user_id` (optional FK to Auth), `person_first_name`, `person_last_name`, `person_document_type`, `person_document_number`, `person_phone`, `person_birth_date`, `person_created_at`, `person_updated_at`                                                     |
| `membership`            | `membership_id`, `tenant_id` (required FK), `person_id` (composite tenant/person FK), `membership_role`, `membership_status`, `membership_valid_from`, `membership_valid_to`, `membership_created_at`, `membership_updated_at`                                                                        |
| `membership_permission` | `membership_permission_id`, `tenant_id` (required FK), `membership_id` (composite tenant/membership FK), `membership_permission_admin_permission`, `membership_permission_created_at`, `membership_permission_updated_at`                                                                             |
| `audit_event`           | `audit_event_id`, `tenant_id` (nullable for platform events), `audit_event_actor_user_id`, `audit_event_actor_person_id`, `audit_event_action`, `audit_event_table_name`, `audit_event_row_id`, `audit_event_diff`, `audit_event_occurred_at`, `audit_event_request_ip`, `audit_event_request_device` |

Person uniqueness is scoped to `(tenant_id, user_id)` when bound to Auth, and to `(tenant_id, person_document_type, person_document_number)` when a document is present. Document type and number are provided together. One human can have independent person rows in different tenants; no cross-tenant document search is exposed. Membership validity windows must be nonempty. Permission assignments are unique by tenant, membership and permission.

Every tenant key and foreign key is indexed, using primary/unique indexes where those already provide the required prefix. The schema guard checks foreign key index coverage. No unit, gate, device, or later-module tables were created; the membership table comment records the deferred M02 unit relationship.

Enums contain the task/glossary values: `membership_role` (four tenant roles), `membership_status` (active/suspended/revoked), `admin_permission` (nine granular permissions), and `tenant_subscription_status` (pilot/active/suspended/cancelled). `document_number` and `phone_number` are reusable text domains limited to 1–32 characters. No financial fields or unused money domain were added.

## Authorization helpers

These five SQL helpers are `STABLE SECURITY DEFINER`, have an empty `search_path`, and use qualified relations. They are in `app_private`, outside the configured PostgREST schemas. Only authenticated users receive schema usage and execute access to these helpers; trigger functions are not executable by clients. Calls to `auth.uid()` and `auth.jwt()` use scalar subqueries as advised by the [Supabase RLS documentation](https://supabase.com/docs/guides/database/postgres/row-level-security).

| Helper                                         | Behavior                                                                                                |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `current_person_ids()`                         | Returns the current user's person IDs with at least one currently active membership in that tenant      |
| `is_tenant_member(uuid)`                       | Checks Auth identity, tenant, active status, and validity window                                        |
| `has_tenant_role(uuid, membership_role[])`     | Adds a matching role requirement to the active membership check                                         |
| `has_admin_permission(uuid, admin_permission)` | Requires an active tenant-admin membership and a matching permission assignment on that same membership |
| `is_platform_admin()`                          | Requires an active platform-admin record for `auth.uid()` and the signed JWT `aal = aal2`               |

Active means `membership_status = active` and `membership_valid_from <= now() < membership_valid_to`, with an unbounded upper limit when valid-to is null. Permissions on expired, future, suspended, revoked, or upper-boundary memberships grant no access. Helpers query base tables as the database owner, avoiding recursive membership RLS evaluation.

## Policies and write protections

Policies are separate per operation and restricted to `authenticated`. Anonymous privileges are revoked. Authenticated users get only SELECT/INSERT/UPDATE/DELETE on mutable tables; audit gets SELECT only.

| Table                   | SELECT                                                                                                    | INSERT                                        | UPDATE                                        | DELETE             |
| ----------------------- | --------------------------------------------------------------------------------------------------------- | --------------------------------------------- | --------------------------------------------- | ------------------ |
| `tenant`                | Active tenant members or MFA platform admin                                                               | MFA platform admin                            | `tenant_settings` admin or MFA platform admin | MFA platform admin |
| `platform_admin`        | MFA platform admin                                                                                        | MFA platform admin                            | MFA platform admin                            | MFA platform admin |
| `person`                | `registry` admin, tenant guard, own person with active membership, or MFA platform admin                  | `registry` admin or MFA platform admin        | Same                                          | Same               |
| `membership`            | `registry` admin, own person's memberships while that person has active membership, or MFA platform admin | `registry` admin or MFA platform admin        | Same                                          | Same               |
| `membership_permission` | `registry` admin or MFA platform admin                                                                    | `registry` admin or MFA platform admin        | Same                                          | Same               |
| `audit_event`           | `access_audit` tenant admin or MFA platform admin                                                         | Audit trigger only; no client grant or policy | Denied                                        | Denied             |

UPDATE policies check both the old and resulting rows. A metadata trigger prevents tenant reassignment and primary key mutation and maintains timestamps. A separate invoker trigger rejects subscription-status changes by tenant admins, even if they have `tenant_settings`; MFA platform admins may change it. Permission assignment locks the parent membership and requires a tenant-admin role, and role changes require removal of incompatible permission rows first. This serializes assignments against concurrent membership-role changes.

Every permission check is resolved from the authenticated identity and its active memberships; client-supplied tenant IDs alone never grant access. Platform-admin records are separate from memberships and do not provide tenant roles.

## Audit behavior and extension

`app_private.audit_row_change()` is attached to tenant, person, membership, membership_permission, and platform_admin. Every successful INSERT/UPDATE/DELETE emits a same-transaction event: full new row on insert, full old row on delete, or only changed keys as `{column: {old, new}}` on update. An update with no changed values emits no event. Actor identity comes from `auth.uid()`; actor person is resolved only in the affected tenant. Headers provide optional IP (`x-forwarded-for`) and device (`x-device-id`), bounded to 256 characters and treated as untrusted context. Missing or malformed header settings yield null metadata.

To extend audit to a future sensitive table, attach the documented function as an `AFTER INSERT OR UPDATE OR DELETE FOR EACH ROW` trigger. It requires a UUID `<table>_id` column, and uses `tenant_id` when present. The migration and SQL function comment document this contract.

Audit privileges and policies prevent client writes. An additional trigger rejects UPDATE, DELETE, TRUNCATE and direct INSERT even by the table owner; inserts are accepted only through nested audit triggers. Historical tenant, actor and source row IDs deliberately have no foreign keys: source deletion must preserve the original audit without changing or removing history. IDs are captured by the trusted trigger rather than supplied by a client. Database owners can still alter database definitions, as is inherent in PostgreSQL ownership; the immutability tests cover normal owner DML and TRUNCATE.

Interpretation recorded for review: the requirement that expired/suspended/revoked memberships grant nothing takes precedence over unconditional self-profile reads.
